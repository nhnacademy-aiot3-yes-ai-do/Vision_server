# Vision 개발 회고와 취업 문서 활용

기준일: 2026-09-14 · [문서 안내](README.md) · [개발 사건](DEVELOPMENT_HISTORY.md) · [근거](EVIDENCE.md)

이 문서는 확인된 개발 경험을 어떤 역량으로 설명할지 정리한다. 완성된 자소서가 아니라 **지원 직무와 실제 개인 담당 범위에 맞게 다듬을 초안**이다. 서비스 기능과 수치는 [API](../../API.md)와 [모델 카드](../../MODEL_CARD.md)의 한계를 함께 인용한다.

## 1. 핵심 회고

### 데이터를 많이 확보하는 것보다 라벨이 무엇을 의미하는지 확인하는 일이 먼저였다

라벨 JSON 332,100개를 조사했지만 갓·대·무게의 정답 값은 없었다. 데이터 규모만 보고 수확·크기 예측을 약속할 수 없다는 점을 확인했다. 품종 탐지와 건강 상태 분류로 범위를 정한 것은 단순한 기능 축소가 아니라 **근거가 있는 결과만 서비스에 내보내기 위한 선택**이었다. V01·V02, EVIDENCE의 VE01·VE03 참조.

### 높은 점수를 설명할 수 있어야 검증이라고 말할 수 있었다

이미지 이름이 겹치지 않아도 촬영 세션·카메라·날짜가 겹칠 수 있었다. 날짜·카메라를 분리했지만 상태별 촬영 시기가 다르다는 편향은 남았다. 따라서 내부 Accuracy를 외부 농가 성능으로 바꾸어 말하지 않았다. 이 경험은 ‘점수를 높였다’보다 **점수의 조건과 한계를 점검했다**는 사례로 설명하는 편이 정확하다. V03·V04·V06, VE02·VE05·VE07·VE09 참조.

### 모델의 불확실성을 숨기지 않는 것도 구현이었다

잘못 탐지한 영역을 분류기에 보내면 그럴듯한 건강 점수가 나올 수 있다. 탐지 단계가 불충분하면 분류를 생략하고, 분류 결과가 낮은 신뢰도이면 판정을 보류하도록 구분했다. `UNCERTAIN`, 확률 `null`, 미탐지·서버 오류 구분은 단순 부가 문구가 아니라 **실패 원인이 전달되는 API 계약**이다. V07·V08, VE10 참조.

### 연구 결과를 팀원이 사용할 수 있는 형태로 넘겨야 서비스가 됐다

모델 파일 외에도 클래스 순서, 해시, 실행 환경, 이미지 입력 제한, 준비 상태, 오류 응답을 정리해야 Java 서비스와 연결할 수 있었다. 코드가 실행되는 것과 다른 서비스가 안전하게 호출할 수 있는 것은 다른 문제였다. V09~V11, VE11~VE15 참조.

## 2. 남아 있는 문제와 다음 검증

다음은 완료한 성과가 아니다. 향후 실제로 수행한 뒤 입력·버전·조건·결과를 추가한다.

| 우선 과제 | 지금 부족한 근거 | 다음에 남길 기록 |
| --- | --- | --- |
| 외부 일반화 | 독립적인 스마트폰·새 농가 평가 미완료 | 출처가 허용된 이미지, 촬영 조건, 정답 확인 방법, 모델별 지표와 실패 사례 |
| 날짜·배경 편향 | split 분리만으로 원인 제거를 증명하지 못함 | 동일 평가 조건의 원본/배경/마스킹 비교, 클래스·촬영 조건별 오류 |
| 평가 재현성 | 일부 원 `results.csv`, `args.yaml` 미확보 | 데이터 manifest·설정·학습 로그·모델 SHA·평가 버전을 연결 |
| 추론 비용 | 실제 CPU 메모리·latency·동시 요청 성적표 부족 | 장비·프로세스/worker·해상도·warm-up·반복 조건과 raw 측정 결과 |
| 사용자 유용성 | ‘Vision 설명이 부실하다’는 실제 피드백 원문 미확보 | 입력 Context, 생성 문장, 분석 사진, 개선안과 평가 기준 |
| 운영 일치 | 현 코드와 실제 운영 모델의 일치 여부 미확인 | 배포 image SHA, 모델 manifest, ready 상태, 실제 API 응답 |

사용자 피드백을 보강하더라도 병명·병반·수확일을 LLM이 추측하게 만들면 안 된다. 먼저 **분석한 사진·영역, 결과의 의미와 한계, 불확실한 이유, 다음 확인 행동**을 실제 출력 근거에 맞춰 제공한다. 과거 사진 비교와 성장량 추정은 별도 기능이다.

## 3. 포트폴리오에 담을 세 가지 사례

### 사례 A — 데이터 검증으로 구현 범위를 결정

- 문제: 크기·생육·수확 판단 요구와 라벨의 지원 범위가 불명확했다.
- 행동: 전체 JSON 구조·결측·라벨 의미를 조사하고 가능한 기능을 분리했다.
- 결과: 품종 탐지·건강 분류에 집중하고 지원하지 않는 기능을 명시했다.
- 증거: VE01·VE03·VE04, 현재 모델 카드.
- 강조 역량: 요구사항 구체화, 데이터 해석, 범위·위험 관리.

### 사례 B — 점수보다 평가 신뢰성 점검

- 문제: 고정 카메라·날짜 조건과 건강 상태가 연관되어 내부 점수가 과대평가될 가능성이 있었다.
- 행동: 그룹 중복과 메타데이터 편향을 조사하고 건강 Train/Validation을 날짜·카메라로 분리했다.
- 결과: 내부 평가와 남은 편향을 함께 기록했다. 완전한 누수 제거라고 주장하지 않았다.
- 증거: VE02·VE05~VE09.
- 강조 역량: 원인 가설 수립, 실험 조건 해석, 한계에 대한 설명 책임.

### 사례 C — 모델을 실패 상태까지 정의한 API로 연결

- 문제: 모델 출력만으로는 Java 서비스가 입력 오류·미탐지·저신뢰·서버 오류를 구분하기 어려웠다.
- 행동: multipart 계약, 입력 제한, 탐지→분류 gate, 모델 무결성·준비 상태, 오류 코드를 구성했다.
- 결과: 정상 응답뿐 아니라 불확실성과 실패도 구분하는 서비스 계약·테스트를 남겼다.
- 증거: VE10~VE15.
- 강조 역량: 백엔드 API 설계, 서비스 간 연동, 검증·운영 가능성 고려.

## 4. 이력서 문장 초안

**백엔드·AI 서비스 지원용**

> AI-Hub 버섯 라벨 332,100개를 분석해 구현 범위를 정하고, YOLO11n 탐지·YOLO11n-cls 건강 분류를 연계한 FastAPI와 저신뢰 결과 보류 정책을 구현·검토했습니다.

**서비스 안정성 강조용**

> 이미지 입력 제한, 모델 무결성·클래스 매핑 검증, 일회 로드와 준비 상태, 미탐지·불확실·과부하 응답을 정의해 Java 서비스와 연동 가능한 추론 API를 구성했습니다.

사용 전에 해당 범위를 본인이 설명할 수 있는지 확인한다. 도움을 받은 코드를 모두 직접 작성했다고 바꾸거나, 테스트 코드의 존재를 실제 전체 테스트 통과 수로 표현하지 않는다.

## 5. 자소서 경험 초안

### 데이터의 한계를 기능의 경계로 바꾸었습니다

> 버섯 사진 분석 기능을 개발하며 모델을 선택하기 전에 정답 라벨이 요구사항을 뒷받침하는지 확인했습니다. 전체 JSON 332,100개를 조사한 결과 크기·무게 관련 필드는 모두 비어 있었고, 생육 단계 라벨도 찾지 못했습니다. 이에 수확 시기나 실측 크기를 임의로 추정하는 대신 품종 탐지와 정상·병해 의심 분류로 범위를 정했습니다. 이후 촬영 날짜와 카메라가 학습·검증에 겹칠 가능성을 조사하고 분리 조건을 강화했습니다. 내부 점수가 높더라도 새 촬영 환경의 성능을 보장하지 않는다는 한계를 문서와 API에 남겼습니다. 이 경험을 통해 AI 기능의 완성도는 모델 점수뿐 아니라 데이터의 의미와 실패 시 동작을 명확히 하는 데 달려 있음을 배웠습니다.

기업별로 마지막 문장을 직무와 연결하되, 지원 회사가 요구하는 기술을 이미 사용한 것처럼 추가하지 않는다. ‘저 혼자 모든 것을 해결했다’보다 실제 개인 판단과 팀 인터페이스를 구분한다.

| 예상 질문 | 답변의 중심 | 피할 주장 |
| --- | --- | --- |
| YOLO를 직접 만들었나요? | 기존 YOLO11n 계열을 버섯 데이터에 맞춰 학습·검증하고 서비스 연결 | 신경망 구조를 처음부터 독자 설계 |
| BFS/DFS로 탐지하나요? | 신경망의 이미지 특징 기반 bbox·품종 예측 | 그래프 탐색 알고리즘으로 버섯 위치 탐색 |
| 왜 모델을 둘로 나눴나요? | 위치·품종 탐지와 crop 건강 분류의 task 및 라벨 단위 구분 | 모든 개체의 병명까지 개별 확진 |
| 왜 n 모델인가요? | 작은 모델과 통일된 도구체계, CPU 서비스에 맞추는 선택 | 비교 자료 없이 ‘가장 빠르고 정확하다’ |
| 99.9%면 실사용 가능한가요? | 해당 건강 Validation의 결과, 촬영 조건 편향과 외부평가 필요 | 실제 농장 정확도 99.9% |
| 15% padding은 최적인가요? | 이미지 크기 기준 context 보존 정책, 최적 비교는 미확인 | 성능을 가장 높인 최적값 |
| UNCERTAIN은 어떻게 학습했나요? | 별도 클래스가 아니라 탐지/분류 점수에 따른 서비스 보류 | 불확실 클래스 학습 또는 확정 발병 확률 |
| 배포와 성능 검증은 어디까지 했나요? | 코드·설정·실행 로그가 확인되는 환경만 구분해서 답변 | 문서 존재만으로 전 플랫폼·운영 완료 |

## 7. 제출 전에 고칠 표현

| 과장되거나 모호한 표현 | 근거에 맞는 표현 |
| --- | --- |
| 33만 장으로 모델을 학습했다 | 라벨 JSON 332,100개를 조사했고, 건강 분류 Train 5,000/Validation 1,000장을 구성했다 |
| 데이터 누수를 없앴다 | 날짜·카메라 분리를 적용했고 남은 촬영 조건 편향을 기록했다 |
| 병충해를 정확히 진단한다 | 정상·병해 의심을 분류하며 병명·해충을 확진하지 않는다 |
| 사진 속 모든 버섯을 진단한다 | 탐지된 품종별 union 영역을 건강 분류한다 |
| 모델 confidence가 발병률이다 | 모델의 출력 점수이며 실제 발병 확률로 보정된 근거는 없다 |
| 처리속도를 크게 개선했다 | 동시성·로드 정책을 구성했다. 속도 개선 수치는 실측 근거 확보 후 기재한다 |
| 모델·배포를 모두 완료했다 | 현재 코드·승인 모델과 실제 운영 확인 범위를 나눠 명시한다 |

마지막으로, 원래 실험 결과를 기억으로 보충하지 않는다. 확인되지 않는 값은 비워두고 [EVIDENCE.md](EVIDENCE.md)에 어떤 원자료가 더 필요한지 추가한다.
