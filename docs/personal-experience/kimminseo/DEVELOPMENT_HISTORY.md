## 4. 사건 기록

### V01. 많은 데이터를 확보했지만, 요구 기능에 필요한 정답이 있는가?

**문제/제약:** 초기 기획에는 크기나 생육·수확 판단 기대가 있었다. 파일이 많다는 사실만으로 해당 기능을 학습할 수 있는지는 알 수 없었다.

**확인한 근거 [보고서 확인]:** 2026-07-26 전체 라벨 JSON **332,100개**를 스트리밍으로 조사했고 처리 실패는 0개였다. 갓 직경·갓 두께·대 길이·대 두께·총중량은 각각 유효값 0개, 결측률 100%였다. 생육 단계와 유사한 이름의 필드도 찾지 못했다. 이미지 ZIP은 중앙 디렉터리의 파일명만 확인했으며 전체 이미지 바이트를 읽거나 디코딩하지 않았다. [VE01]

**선택과 구현:** 전체 압축을 먼저 해제하거나 학습부터 시작하지 않고, JSON의 품종·작업·정상 여부·bbox·결측을 집계했다. 중복 집계는 SQLite를 사용하고 전체 키를 메모리에 한꺼번에 보관하지 않는 방식으로 조사했다. [VE01, VE02]

**결과:** 현재 데이터로 뒷받침 가능한 품종 탐지·건강 상태 분류를 중심으로 범위를 축소했다. 데이터가 없는 물리량·수확일을 모델 출력처럼 만들지 않았다.

**남은 한계:** JSON 분석 성공은 이미지 무결성 전체 검사 성공이 아니다. 라벨 유무를 조사한 것이며 농업적으로 모든 라벨이 정확함을 증명한 것도 아니다.

**경험의 의미:** 구현 이전에 데이터와 요구사항의 간극을 찾아 불가능하거나 과장되기 쉬운 기능을 걸러낸 경험이다.

### V02. ‘수확 모델’ 파일이 있다고 수확 시기를 알 수 있는 것은 아니었다

**문제:** AI-Hub 제공 자료의 수확 관련 모델을 이용하면 처음 요구를 구현할 수 있을지 검토할 필요가 있었다.

**조사 [보고서 확인]:** 제공 설정에는 YOLOv3-tiny/YOLOv4 계열의 품종+번호 단계 객체 탐지 구조가 있었지만, 최종 task 가중치와 `_1/_2/_3`의 명확한 단계 의미, 수확 가능 상태로 바꾸는 매핑을 확인하지 못했다. 관련 파일명이 수확을 암시해도 실제 의미를 복원할 근거는 부족했다. [VE03]

**판단:** Windows/CUDA 실행 환경만 맞추면 해결되는 문제로 보지 않았다. 가중치·클래스 의미·추론 규칙이 먼저 필요했다. 현재 서비스의 지원 범위에서 수확 적기를 제외했다.

**주의:** 이것은 제공 패키지의 **정적 검토**이지, 해당 모델을 실제 실행해 수확 정확도가 낮았음을 입증한 실험이 아니다. 팀의 수확 모드 전환 기능과 Vision 수확 시기 예측도 별개의 기능이다.

### V03. 파일명이 중복되지 않아도 촬영 조건이 겹칠 수 있었다

**문제:** 원본 Training/Validation을 그대로 사용하면 비슷한 사진·촬영 조건이 양쪽에 포함되어 높은 점수가 나올 가능성이 있었다.

**조사 [보고서 확인]:** 동일 이미지 파일명·stem 중복은 0이었지만, 품종+카메라+날짜+시간 촬영 세션 중복 키는 **994개**, 카메라+날짜 중복 키는 **560개**였다. 이것은 메타데이터 기반 중복 신호이며 픽셀 유사도 검사나 누수 인과 증명은 아니다. [VE02]

**선택:** 배양 bbox가 주로 병·봉지·배지를 가리킨다는 라벨 의미를 고려해 배양 데이터를 제외했다. 생육·병해 중 유효 bbox가 있는 데이터로 탐지 후보 manifest를 만들고 그룹 단위로 분리했다. 이후 camera holdout pilot 단계가 이어졌다. [VE04, VE14]

**확인된 중간 산출물:** 탐지 후보 manifest에는 JSON 303,388개와 bbox 575,702개가 포함되었다. 이 단계에서 선언한 그룹의 split 중복은 0이었다. **이 수치는 후보 manifest 규모이지 실제 detector 학습 이미지 수가 아니다.** [VE04]

**교훈:** ‘동일 파일 없음’과 ‘새 환경에 일반화됨’은 다른 주장이다. 초기 탐지 manifest의 `species+camera+date` 분리와 최종 건강 분류의 전역 날짜+카메라 분리를 하나의 실험처럼 섞지 않는다.

### V04. 정상/병해 라벨보다 촬영 날짜를 외웠을 가능성을 의심했다

**문제 [가설/검토]:** 정상과 병해 촬영 시기·작업 폴더가 강하게 연결되어 있었다. 높은 분류 점수가 버섯의 건강 특징이 아니라 촬영 조건을 구분한 결과일 수 있었다.

**진단 [보고서 확인]:** 같은 데이터 안에서 메타데이터 다수결 lookup을 했을 때 날짜만으로 93.79%, 품종+날짜로 97.59%, 날짜+카메라로 95.30%의 상태를 맞힐 수 있었다. 이것은 **학습 모델 성능이 아니라 편향 위험을 확인하는 진단치**다. raw/masked 이미지 대응 조사도 했지만 마스킹의 존재 자체가 다른 단서가 될 가능성이 남았다. [VE05]

**선택:** 단순 무작위 분할을 신뢰하지 않고 전역 촬영 날짜와 global camera ID가 Train/Validation에 겹치지 않는 건강 분류 세트를 구성했다. 5품종×2상태마다 학습 500장·검증 100장, 총 학습 5,000장·검증 1,000장이다. [VE06]

**남은 한계:** 정상 검증 사진은 2021-11-04, 병해 검증 사진은 2021-11-26/12-04에만 있었다. 분할 간 날짜 중복을 없앴어도 **날짜와 건강 상태의 상관관계가 사라진 것은 아니다.** 원본 고정 Test까지 포함해 모든 날짜를 분리한 균형 3-way split은 가용량 제약이 있었다. [VE05, VE07]

**쓰지 말 표현:** ‘데이터 누수를 완전히 제거했다’, ‘timestamp를 지워 정확도가 개선됐다’. 완전한 원인 분리 실험과 동일 조건 개선 근거가 없다.

### V05. 건강 라벨은 이미지 단위인데 탐지 결과는 여러 영역이었다

**문제:** 가장 큰 버섯 하나만 잘라 분류하면 이미지 단위 건강 라벨의 범위와 맞지 않을 수 있다. 전체 사진을 넣으면 재배실 배경까지 과도하게 사용한다.

**선택 [보고서·코드 확인]:** 같은 품종의 모든 bbox를 합친 union 영역에 **원본 이미지 폭·높이 기준 15%를 각 방향으로 padding**하고 경계를 잘랐다. 품종 그룹마다 건강 분류를 한 번 수행한다. bbox 크기의 15%가 아니다. [VE08]

**기대 효과와 검증:** 다른 개체·군집 누락을 줄이고 주변 문맥을 일부 남기는 설계다. 내부 end-to-end 100장에서는 detector crop과 정답 bbox crop의 건강 상태가 모두 일치했다. 다만 전체 이미지·10%·15%·20%를 동일 조건으로 비교해 15%가 최적이라고 확정한 자료는 없다. [VE07]

**중요한 제한:** bbox는 병반 위치가 아니다. 같은 품종 그룹에 대한 판정을 사진 속 모든 개체의 개별 진단으로 해석하면 안 된다. 탐지 객체 수 역시 가림·군집 annotation 때문에 실제 버섯 총개체수와 같다고 보장할 수 없다.

### V06. 내부 점수는 높았지만 실제 농장 성능처럼 말하지 않기로 했다

**검증 [보고서 확인]:** 건강 분류 Validation 1,000장 중 999장이 정답이었다. 정상 500장 중 1장을 병해 의심으로 분류했고, 병해 의심 500장은 모두 맞혔다. [VE09]

**구분한 것:** detector mAP, 건강 classifier Accuracy/F1, 두 모델을 연결한 end-to-end 검사, API 계약 테스트는 서로 다른 검증이다. 같은 숫자 축에서 비교하거나 합산하지 않는다.

**판단:** 제한된 내부 데이터와 촬영 환경 편향을 공개하고 외부 스마트폰 독립 평가를 후속 과제로 남겼다. 단순히 ‘99.9% 정확도 AI’라는 식의 홍보를 피한다.

**개선 과제:** 새 농가·카메라·조명·거리의 독립 Test, 배경만으로 분류되는지 보는 대조 실험, 데이터/모델 버전과 raw 실행 로그 보존. 아직 완료한 성과로 적지 않는다.

### V07. 잘못 탐지한 영역으로 건강 분류까지 강행하지 않도록 했다

**위험:** detector가 낮은 신뢰도로 잘못 잡은 영역을 classifier에 넘기면 그럴듯한 건강 확률이 나올 수 있다. 최종 건강 confidence만 검사하면 앞단 실패를 놓친다.

**구현 [코드 확인]:** 기본 탐지 후보 threshold는 0.25다. 품종 그룹 내 최소 탐지 confidence가 0.50 미만이면 classifier를 실행하지 않고 `UNCERTAIN`과 건강 확률 `null`을 반환한다. 탐지를 통과해 분류했더라도 건강 top-1 confidence가 0.70 미만이면 `UNCERTAIN`을 반환하되 실제 분류 확률은 남긴다. 0.50/0.70과 정확히 같은 값은 ‘미만’ 조건에 해당하지 않는다. [VE10]

**검증 기록:** 저신뢰 탐지, 경계값, 품종별 격리 테스트가 있다. 2026-07-29 `fix: skip health analysis for low-confidence detection` 이력이 조치의 존재를 뒷받침한다. 원래 어떤 외부 사진 한 장이 이 수정을 직접 유발했는지는 확보된 자료로 확정하지 못했다.

**의미:** `UNCERTAIN`은 따로 학습한 세 번째 클래스가 아니라 서비스의 판정 보류 정책이다. confidence 또한 보정된 실제 발병 확률이 아니다.

### V08. 버섯 미탐지와 서버 오류를 구분했다

**문제:** 이미지에 지원 버섯이 없거나 탐지가 실패한 경우를 모두 500으로 처리하면 사용자는 입력의 문제인지 서버의 문제인지 알 수 없다.

**구현 [코드 확인]:** 분석을 마쳤지만 객체가 없으면 HTTP 200 + `NO_MUSHROOM_DETECTED`, `results=[]`를 반환한다. 손상·형식·크기 오류는 400/415/413, 분석 용량 초과는 429, 내부 추론 오류는 500으로 분리했다. 한 품종의 낮은 confidence가 다른 품종 분석까지 막지 않는다. [VE10, VE11]

**주의:** `NO_MUSHROOM_DETECTED`는 ‘사진에 버섯이 절대로 없다’는 정답 선언이 아니라 현재 모델이 탐지하지 못했다는 결과다. 외부 웹 이미지 실패·오분류 경험은 기존 대화에 있었지만 비민감 원본 사진+모델 버전+출력 로그가 이번 조사에서 확보되지 않아 정식 외부 평가로 기록하지 않는다.

### V09. 실험 스크립트를 Java 서비스가 호출할 수 있는 API로 바꿨다

**문제:** 로컬 이미지 경로를 받아 실행하는 연구 코드만으로는 팀 서비스가 안정적으로 사용할 수 없다.

**구현 [코드 확인]:** Spring AI Server가 저장소에서 받은 이미지 바이트를 multipart `image`로 보내면 FastAPI가 검증→추론→camelCase JSON 응답을 반환하도록 계약을 정리했다. Vision이 사진 저장소를 직접 읽거나 업로드 사진을 영구 저장하는 구조는 아니다. 동기 HTTP 응답이므로 별도 완료 polling/callback은 필요하지 않다. [VE11]

**안전장치:** 확장자·MIME·실제 이미지 형식 일치, JPEG/PNG/WEBP 제한, 기본 10MiB 상한, 픽셀 제한, 손상 파일 거부, EXIF 방향 보정, 공개 오류에서 내부 경로 비노출을 처리한다.

**동시성 [코드 확인]:** 이미지 바이트·디코딩 객체 보유 요청 수를 프로세스별로 제한하고 용량이 차면 429를 반환한다. 모델 호출은 lock으로 직렬화하며 동기 작업은 executor에서 수행한다. 요청 취소가 작업 스레드를 즉시 멈춘다고 가정하지 않는다. 이 admission은 FastAPI의 multipart 수신 이후 계층으로, 네트워크 전체 업로드를 사전에 차단하는 장치는 아니다. [VE12]

**성과 표현의 한계:** 동시 요청 제어와 테스트가 존재하는 것은 확인했지만, 처리량·메모리·지연시간 개선율을 측정한 결과는 이 문서에 없다.

### V10. 이름이 같은 best.pt라도 같은 모델이라고 믿을 수 없었다

**문제/설계 위험:** 탐지와 건강 분류 파일을 혼동하거나 클래스 순서가 달라지면 서비스가 잘못 해석할 수 있다. 매 요청 로드도 피해야 한다.

**구현 [코드 확인]:** manifest에 역할·버전·경로·파일 크기·SHA-256·입력 크기·class mapping·제한사항을 기록한다. ModelRegistry는 최초 한 번 로드하고 실제 클래스 순서 및 파일 무결성이 맞을 때만 READY로 공개한다. 부분 로드 실패는 캐시하지 않으며 실패 상태를 남긴다. [VE13]

**변경 맥락:** 과거 연구 ref의 `prepare_runtime_models.py`는 승인 모델을 staging하는 방식이었다. 현재 checkout은 두 모델을 Git에서 코드와 함께 관리하며 `verify_runtime_models.py`로 검증하고 image에 포함하는 방식이다. 과거 준비 스크립트를 현재 설치 절차로 안내하지 않는다.

**검증:** singleton·동시 로드·class mapping 불일치·부분 로드 실패·내부 경로 비노출 테스트가 존재한다. 이번 문서화에서는 테스트를 실행하지 않았다.

### V11. Apple Silicon 개발 환경과 Linux CPU 배포 계약을 분리했다

**문제/설계 제약:** Mac 개발 환경과 Linux CPU/CUDA 환경의 의존성·device가 같지 않다. Mac에서 실행됐다는 이유로 운영에서 검증됐다고 말할 수 없다.

**구현·문서 [코드 확인]:** Mac arm64/CPU/MPS 확인 절차, runtime 환경 점검, fake-model 테스트와 실제 모델 opt-in 테스트를 분리했다. Linux amd64 CPU·worker 1·live/ready probe·모델검증+pytest→image build→중앙 배포 요청 계약을 문서화했다. [VE15]

**개인 기여 확인:** 2026-08-23 CPU 배포 준비 변경의 author와 파일 범위가 김민서 담당 설명과 맞는다. 그러나 workflow 파일 존재나 모델 카드의 ‘배포 모델’ 표현은 현재 클러스터 rollout 성공 증거가 아니다.

**추가 확보할 증거:** 실행 환경 버전, 실제 모델 응답, CI run 링크, 배포 image SHA, ready 상태, CPU memory/latency 실측. 이 자료 없이는 ‘전 플랫폼 검증 완료’, ‘최신 운영 배포 완료’를 쓰지 않는다.

### V12. 발표를 준비하면서 학습 방식과 수치의 의미를 다시 정리했다

**대화에서 드러난 혼동 [사용자 설명]:** YOLO 탐지 방식을 BFS 같은 탐색 알고리즘으로 설명할지 고민했고, 1,000장 Validation을 ‘정답 데이터’로 불렀으며 332,100 라벨 수와 6,000장 학습·검증 입력 수가 혼재했다.

**정리한 개념:** YOLO는 신경망 기반 객체 탐지 모델이며 BFS/DFS로 버섯을 탐색한 구현이 아니다. 정답 라벨을 사용하는 지도학습이고, 학습 세트와 검증 세트 모두 정답 라벨이 있다. 탐지 모델은 위치·품종, 분류 모델은 정상/병해 의심을 다룬다. 건강 분류 6,000장은 학습 5,000+검증 1,000이지 각 모델에 3,000장을 썼다는 뜻이 아니다.

**회고 포인트:** 구현을 수행한 것과 다른 개발자에게 평가 조건·작동 원리를 명확히 설명하는 것은 별도의 역량임을 확인했다. 이 경험을 ‘모든 모델 구조를 직접 설계했다’로 과장하지 않는다.

### V13. 모델 판정이 있어도 사용자 피드백은 빈약할 수 있다는 의견을 받았다

**사건 [사용자 설명]:** 팀원이 일일 피드백의 Vision 부분이 부실하다고 평가했다. 해당 실제 피드백 원문은 이 기록에서 확보하지 못했다.

**현재 판단 [가설/검토]:** 품종·정상/병해 판정을 나열하는 것과 사용자가 이해하고 다음 행동을 정할 수 있게 설명하는 것은 다르다. 하지만 이를 보완하려고 변색 위치·특정 병명·원인을 LLM이 추측하게 해서는 안 된다.

**개선 방향 [계획]:** 분석한 사진과 분석 대상 영역, 결과의 의미·한계, 불확실/미탐지 이유, 후속 확인 행동을 함께 제공한다. 사진의 박스는 ‘병변 위치’가 아니라 ‘분석 대상 영역’으로 표시한다. 과거 사진 비교·성장량 측정은 별도 기능이며 현재 결과만으로 말하지 않는다.

**아직 결과 없음:** 실제 입력 Context와 생성 문단을 비교해 원인을 판별하고 개선 전후 평가해야 한다. 프롬프트나 화면을 개선해 유용성이 높아졌다는 성과는 아직 쓸 수 없다.

## 7. 면접에서 답할 수 있어야 할 질문

**Q. 왜 YOLO11n과 YOLO11n-cls인가요?**

A. 객체 위치·품종을 찾는 탐지와 crop의 건강 상태 분류는 다른 task이므로 두 모델로 나눴습니다. 같은 Ultralytics 계열에서 학습·추론·배포 코드를 연결하고 작은 모델을 CPU 서비스 계약에 맞추는 선택이었습니다. 다만 다른 모델과 동일 조건의 속도·정확도 비교를 보존한 근거는 없으므로 ‘가장 빠르거나 최고 성능이라 선택했다’고는 말하지 않겠습니다. 선택 당시 세부 비교 실험은 추가 확인 대상입니다.

**Q. 직접 모델을 만든 건가요? 머신러닝인가요?**

A. 머신러닝 중 딥러닝을 활용했습니다. 새로운 신경망 구조를 처음부터 설계한 것이 아니라 YOLO11n 계열 모델을 정답 라벨이 있는 버섯 데이터에 맞춰 학습·검증하고 추론 API로 연결한 것입니다.

**Q. BFS/DFS 같은 탐색을 사용했나요?**

A. 그렇지 않습니다. 신경망이 이미지 특징을 이용해 bbox와 품종 점수를 예측하는 객체 탐지입니다. 그 결과를 품종별로 묶어 건강 분류 입력을 구성했습니다.

**Q. 왜 99.9%인데 외부 평가는 필요하죠?**

A. 그 값은 특정 AI-Hub 건강 Validation의 결과입니다. 날짜와 상태의 상관관계, 고정 카메라 환경이 남아 있어 새 스마트폰·농가에 같은 정확도가 나온다고 보장할 수 없습니다.

**Q. 정상 판정이면 병이 없다는 뜻인가요?**

A. 모델이 해당 crop을 정상 클래스로 분류했다는 뜻입니다. 모든 병해가 없음을 보증하지 않으며 특정 병명도 진단하지 않습니다.

**Q. UNCERTAIN 모델을 따로 학습했나요?**

A. 아닙니다. 탐지가 불충분하면 분류를 건너뛰고 확률을 null로 남깁니다. 분류는 했지만 점수가 낮으면 확률을 남긴 채 판단을 보류하는 서비스 정책입니다.

**Q. 15% padding이 최적인가요?**

A. 여러 객체와 문맥을 보존하기 위한 운영 정책입니다. 내부 연결 평가 기록은 있지만, 10%·20%보다 우수함을 확정하는 동일 조건 비교 실험은 확보하지 못했습니다.

**Q. 모든 환경에서 배포 검증했나요?**

A. Mac 로컬 검증 절차와 Linux CPU 배포 계약을 구분해 작성했습니다. 환경별 실제 실행 결과가 확인되는 범위만 완료로 설명하며, CUDA/MPS/운영 rollout을 문서만 보고 완료라고 말하지 않습니다.
