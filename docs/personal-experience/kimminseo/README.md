# 김민서의 Vision Server 개발 경험 기록

기록 기준일: **2026-09-14**

## 이 문서의 목적

MushMush에서 Vision 기능을 개발하면서 확인한 문제, 선택한 방식, 구현·검증 결과, 아직 해결하지 못한 한계를 보존한다. 나중에 포트폴리오·자기소개서·이력서·면접 답변을 작성할 때 당시 근거를 다시 찾기 위한 **개인 경험 아카이브**다.

서비스 사용법은 [API 문서](../../API.md), 모델의 현재 지원 범위와 성능 해석은 [모델 카드](../../MODEL_CARD.md)를 먼저 따른다. 이 폴더는 과거 판단을 설명하는 기록이며, 향후 바뀐 실행 절차를 대신하는 운영 가이드가 아니다.

접근 가능한 저장소·보존 보고서·대화를 기준으로 복원했다. ‘모든 사건’이라는 요청의 취지를 최대한 반영했지만, 실제 작업 전체의 완전한 녹취나 증명은 아니다. 기억이 추가되면 날짜·증거·확인 상태와 함께 보완한다.

## 서비스 개요

MushMush는 버섯 재배의 센서·환경 제어·알림과 AI 분석을 결합한 팀 서비스다. Vision Server는 센서 수치만으로 알 수 없는 사진 속 정보를 분석하는 역할을 맡는다.

현재 처리 흐름은 **이미지 입력 검증 → YOLO11n 품종 탐지 → 같은 품종 영역의 union crop → YOLO11n-cls 건강 상태 분류 → JSON 응답**이다.

- 지원 품종: 느타리, 양송이, 큰느타리, 팽이, 표고.
- 건강 상태: `HEALTHY`, `DISEASE_SUSPECTED`; 신뢰도가 부족하면 서비스 정책으로 `UNCERTAIN`.
- 결과 단위: 품종별 탐지 영역과 해당 영역의 건강 상태. 모든 개체를 각각 진단하는 구조가 아니다.
- 지원하지 않는 기능: 특정 병명 확진, 병반 위치, 해충 탐지, 실제 크기·무게, 생육 단계, 수확 적기.
- 연동 경계: Spring AI Server가 확보한 이미지 바이트를 전달하며, Vision Server가 사진 저장소를 직접 읽거나 사용자 이미지를 영구 저장하지 않는다.

## 나의 담당 범위

사용자 설명과 개인 계정의 변경 이력이 교차 확인되는 범위는 다음과 같다. author 기록은 담당 범위 확인 자료이며 단독 저작·작업량의 정확한 증명은 아니다.

| 영역 | 담당 경험 |
| --- | --- |
| 데이터 검토 | AI-Hub 아카이브·JSON 구조, 결측·라벨 의미·품종 및 상태 분포 조사 |
| 범위 결정 | 데이터가 뒷받침하는 품종 탐지·건강 분류로 구현 범위를 정리 |
| 학습·평가 | 학습 입력 선정, 날짜·카메라 분리, 모델 평가와 한계 검토 |
| 추론 서비스 | 탐지→crop→분류 연결, 입력/출력 계약, 저신뢰·미탐지·오류 처리 |
| 재현성과 협업 | 모델 manifest, 실행 환경·테스트·배포 준비 문서화 |

사진 저장소, Cultivation, Notification, 전체 프론트와 인프라를 개인 구현 범위로 확대하지 않는다. AI 개발 도구·팀원의 도움을 받은 코드는 자신이 이해·선택·수정·검증한 역할을 설명한다. 커밋 수·파일 수·서버 수를 개인 기여율로 환산하지 않는다.

## 기록 기준과 확인 수준

| 표기 | 의미 |
| --- | --- |
| 보고서 확인 | 보존된 분석·평가 결과 존재. 이번 문서화에서 재실행한 값은 아님 |
| 코드 확인 | 구현·테스트 코드 존재. 최신 CI나 운영 성공을 자동으로 의미하지 않음 |
| 사용자 설명 | 본인이 대화에서 설명한 경험. 원본 로그가 없으면 별도 표시 |
| 가설/검토 | 설계 판단 또는 가능한 원인. 확인된 장애 원인과 구분 |
| 계획/미확인 | 향후 과제, 추가 확인할 사실. 완료 성과로 사용하지 않음 |

조사 시 현재 checkout은 `b5a9a8e17f9d3cbef3926bf1463794403aacc4df`이며, 보존 연구 브랜치는 `archive/research-reports-2026-07-30`의 `8420e23628f628adad4ebca983c4b59a0db63e79`다. `Makefile`, `app/main.py`, `app/services/mushroom_health_service.py`에는 기존 미커밋 변경이 있었다. 해당 코드의 운영 반영 여부는 별도 확인 대상이다.

문서화 중 모델 재학습·실행·테스트·대규모 데이터 추출·배포를 하지 않았다. 문서 작성 시점과 원래 실험 시점은 다르며, Git 변경일은 작업의 시작·완료 시각과 반드시 같지 않다.

## 수치를 읽는 최소 규칙

- **332,100**은 분석한 라벨 JSON 수이며 전부 학습에 사용한 이미지 수가 아니다.
- **5,000/1,000**은 건강 분류 Train/Validation 수이며 별도 Test 결과가 아니다.
- detector의 **mAP50-95 0.899**, 건강 분류의 **Validation Accuracy 0.999**, 제한된 **end-to-end 100/100**은 서로 다른 검증이다.
- 내부 평가와 외부 스마트폰/실제 농가 성능을 구분한다.
- confidence는 모델 점수이며 보정된 실제 발병 확률로 해석하지 않는다.

## 새 사건을 추가하는 방법

`날짜 또는 순서 → 증상·제약 → 가설 → 확인한 근거 → 내가 한 선택·조치 → 관찰 결과 → 아직 모르는 것`의 순서로 기록한다. 모델·데이터·코드 버전을 함께 남기고, 해결하지 못한 사건도 지우지 않는다. 토큰, 비밀번호, 개인 연락처, 만료형 사진 URL, 내부 접속 주소는 이력에 복사하지 않는다.
